# 事件时间与当天采集准入规则 v1

状态：业务规则已实施；0.1.27 增加指定软件版本、新库和手动重建的历史准入例外。按本轮确认，时间选择顺序为：记录自身时间 → 同文件前一条有效源时间 → 原始文件更新时间。日常采集按选定时间执行北京时间当天准入，不再使用 1970 兜底。以下当天过滤规则仅适用于日常采集；重建期间按原事件时间接收历史，详见 [实施补充](reconstruction-and-device-ownership-0.1.27.md)。

## 1. 时间字段与准入

- `occurred_at` 优先使用记录自身的有效源时间，由策略按已确认的格式、单位和时区转换；缺失时按下节的前序时间、文件 mtime 顺序兜底。禁止填 `1970-01-01`、采集时间或文件创建时间。
- 首次创建事件时，在 writer 事务开始固定本次 `admission_now`，以北京时间自然日比较 `occurred_at` 和 `admission_now`；只有同一天的事件允许新建本地明细及统计/上传任务。
- 选定时间属于昨天及更早、今天首次发现的事件，返回 `ignored(outside_admission_day)`：不写 events，不创建统计或上传待办。源明确给出的历史时间不能用兜底覆盖；未来日期也不符合当天准入。对于缺失源时间的记录，这只能保证按兜底时间筛选，不能保证其真实发生日期。
- 时间缺失且两级兜底都不可用时返回 `ignored(missing_event_time)`；源时间明确存在但非法或单位无法确定时返回 `ignored(invalid_event_time)`，不以兜底掩盖解析错误。
- 丢弃业务事件不等于卡住源游标。公共 writer 在 collection_sources 中原子提交忽略记录累计数、最近原因、读取进度与必要解析状态；详细排障复用现有日志，避免每 5 秒反复读取同一条已拒绝记录；不额外保存被丢弃的事件正文。
- 跨日会话仍可读取旧上下文用于模型识别、稳定身份及累计计数基线，但这些旧记录不能作为新统计事件。累计计数必须正确扣除基线，不能把之前的总用量算到今天。

此规则是首次准入条件，不是每次处理都重新按今天筛选。昨天已经合法落库、今天仍等待统计或上传的事件，继续执行原任务；重试不改 occurred_at，不刷新 created_at。明细依旧从首次 created_at 起保留 14 天；updated_at 和软删除时间 delete_at 不延长保留期，软删明细也在到期时物理清理。

### 1.1 前序时间与文件时间兜底

同一会话文件按原始记录顺序读取，维护最近一次解析成功的原生时间 `last_source_time`，即“前一条有效时间”。只更新读取上下文，不回改前一条事件，不修改 Agent 原文件。

```text
记录有有效源时间：occurred_at = 源时间，更新 last_source_time
记录没有时间，但已有 last_source_time：occurred_at = last_source_time
记录没有时间，也没有前序有效时间：occurred_at = 本批读取时捕获的原始文件 mtime
三者均不可用：missing_event_time
```

- payload_json.meta 中保存 `time_source=source_record/previous_record/file_mtime`；与 Token accuracy 分开，不新增 SQL 表或处理状态。
- `last_source_time` 保存在该来源流的 `decoder_state_json`，和读取游标同事务提交，保证每批 32 行、重启续读都能沿用；切换文件不能复用其他文件或其他 harness 的时间。
- 只有真实源时间更新 last_source_time。继承时间、mtime 兜底不能冒充新的原生时间锚点。解析为有效源时间的历史记录即使不准入统计，也可用于读取上下文。
- 前序规则用于已确认按顺序读取的会话日志；SQLite 多会话记录、API 响应不能仅凭上一行就继承时间，需要按各自原生时间处理。文件 mtime 必须来自实际原始会话文件，不能来自临时副本或数据库备份。
- mtime 在读取时捕获并随批次传递，writer 不重新读取文件元数据。事件一经准入，在其保留期内 occurred_at 与 time_source 冻结；重复读取先查 events，文件后续修改不能让已有事件改日期、产生新修订或再次计数。正常采集按持久化游标续读；明细过期后不在原库中主动回绕游标。
- 原始记录顺序、前序时间锚点随 checkpoint 一起恢复；跨批次不能因为忘记锚点而退回 mtime。新事实修订须由业务内容变化驱动，不能由文件 mtime 的变化驱动。

例如同文件连续三条记录为 `10:00:00、有内容无时间、10:00:03`，中间记录归到 10:00:00，并标记 previous_record。它通常比整份文件最后修改时间更接近相邻日志的时间，但仍是近似归属，不能视为已验证的真实时间。

精度边界：前序时间可能跨越较长间隔或午夜，mtime 属于整份文件而非单条事件。无逐条时间的昨天记录可能因今天的 mtime 被归到今天，今天的记录也可能继承昨天的锚点而被丢弃。采用兜底后，严格的保证是“按选定时间来源执行当天筛选”。已知真实源时间始终优先，不得用兜底把已知历史事件伪装成今天。

从 0.1.27 起，首次新库、发布标记的软件版本和用户手动重建允许历史 raw 全量准入。重建清空本地事件、统计和来源游标，保留设备身份；进度持久化，重启续跑。各来源到达 EOF 后恢复日常当天准入。详情见 [实施补充](reconstruction-and-device-ownership-0.1.27.md)。

删除 event_identity_ledger，不在其他表或 extra 中保存永久逐事件身份摘要。重新初始化后的源事件仍使用发生时间，不能用重装/重放时刻替代；服务端过滤也只依据 occurred_at。没有原生逐条时间的来源仍按前述已约定的前序时间/mtime 规则处理，其近似精度边界不变。

当天准入由公共采集执行器和 writer 实现，不用带当前日期的数据库 CHECK：否则次日更新一条合法的历史待传事件会错误失败。`events.occurred_at` 保持 INTEGER NOT NULL；上传和投影消费者不能重复施加首次采集日期条件。

## 2. 已发现的实现问题

多个适配器在时间缺失时返回 `1970-01-01T00:00:00Z`。该字符串能通过格式解析，但不代表真实业务时间。实施时需移除这种兜底，按上述前序时间与文件时间规则处理；无可用时间或时间非法时返回明确结果。

代码定位：

- [Cursor transcript](../collector/adapters/cursor/src/lib.rs:495)：先读记录 timestamp，再读 message.timestamp，两者都没有则填 1970；后续 Write/StrReplace/Edit 可生成 CodeChanged。
- [Codex](../collector/adapters/codex/src/lib.rs:499)：timestamp 字符串缺失时填 1970。
- [Claude 会话消息](../collector/adapters/claude/src/lib.rs:519)：timestamp 缺失时填 1970。
- [Pi](../collector/adapters/pi/src/lib.rs:225)：timestamp 缺失时填 1970。
- ZCode、OpenCode、WorkBuddy、Doubao Work 等同类兜底，也应按输入归一化路径逐一处理。

这些分支本身不能证明每个工具的真实输出都会缺时间；来源覆盖结论要以实际记录为依据。

## 3. 本机真实样本证据

2026-09-11 对本机已有记录做了只读结构抽样，只输出字段名、记录类型与计数，没有复制聊天正文、工具参数或完整私人路径到仓库。每个来源最多检查最近 5 个 JSONL 文件，每文件最多 1000 行；这不是对所有版本的普查。

| 来源 | 抽样结果 | 能支持的结论 |
| --- | --- | --- |
| Cursor agent-transcripts | 5 个文件，共 396 条解析记录；检查的时间键未出现。包含 191 条 Write/StrReplace/Edit 工具调用候选 | 存在与当前代码统计路径直接相关的真实缺失时间记录 |
| Codex sessions | 5 个文件，共 932 条解析记录均发现时间字段 | 此样本没有发现缺失时间，不推断所有版本都完整 |
| Pi sessions | 本机 2 个文件，共 18 条解析记录均发现时间字段 | 此样本没有发现缺失时间 |
| Claude projects | 发现 atis-latch、last-prompt 等无时间辅助记录；抽样的 user/assistant 消息有时间 | 原始文件并非每行都有时间，但辅助记录不能当作缺失时间的用量事件证据 |
| Grok sessions | chat_history.jsonl 中存在无时间聊天记录；此次抽样的更新/运行日志有时间 | 聊天记录不等于当前用量输入，不能据此断言 updates 用量缺时间 |

Cursor 的一个具体实例位于本机 `agent-transcripts/<会话>/<会话>.jsonl` 第 4 行，是 Write 工具调用：顶层字段仅 `message`、`role`，message 仅有 `content`，tool_use 对象字段为 `input`、`name`、`type`。记录和 message 均没有 timestamp，且工具输入包含可生成代码变更的内容。

下面只是该真实记录的结构摘要，省略全部工具参数，不是复制原文：

```json
{
  "role": "assistant",
  "message": {
    "content": [
      {"type": "tool_use", "name": "Write", "input": {}}
    ]
  }
}
```

按当前 Cursor 适配器逻辑，该记录会用 1970 作为 CodeChanged 的时间。按新方案，先查同文件前序有效源时间，没有则用原始 transcript 的 mtime。此次 Cursor 抽样未找到可继承的原生时间，因此这些样本仍需要文件时间兜底；不能用采集时间替代。

## 4. 实施验收样例

| 场景（北京时间） | 期望 |
| --- | --- |
| 09-11 10:00 发生，09-11 10:00:05 首次入库 | 接受；归入 09-11 对应小时桶 |
| 09-10 23:59 发生，09-11 00:00:01 首次入库 | 丢弃，不写明细/统计/上传待办；推进源进度 |
| 09-10 已合法入库，09-11 上传重试 | 继续原任务，不因跨日丢弃 |
| 源没有时间，但同文件前一条有效时间为今天 10:00 | 用该时间，标记 previous_record，准入今天 |
| 跨批次/重启后第一条记录缺时间 | 从同流 decoder_state 恢复 last_source_time，不因为批次切换直接退回 mtime |
| 源及前序记录都没有时间，原始文件 mtime 为今天 | 使用读取时捕获的 mtime，标记 file_mtime，按今天准入 |
| 源明确给出昨天时间，文件 mtime 为今天 | 使用源时间并丢弃，不能被 mtime 覆盖 |
| 保留期内同一已入库记录被重复读取，文件 mtime 已改变 | 使用 events 中已冻结时间，不创建新修订或重复统计 |
| 记录、前序有效源时间和原始文件 mtime 均不可用 | missing_event_time；不能填 1970 或当前时间 |
| 源时间非法或单位无法确定 | invalid_event_time；不能猜测单位或日期 |
| 同一会话跨两天，今天出现带有效时间的新用量 | 只准入今天的新事件；旧上下文可用于基线，不补记旧用量 |
| 采集执行跨过午夜 | 以首次入库事务固定的 admission_now 判断，不以解码开始时间判断 |
| 原库正常重启/明细清理后继续采集 | 恢复原游标，不从头重放；来源进度不随事件 TTL 删除 |
| 重装并初始化本地数据后重新采集 | 使用源事件时间，仍遵循本地准入规则；服务端按 occurred_at 过滤，不按重放时间 |

所有表的 created_at、updated_at、delete_at 保持独立整数列；extra 是本地扩展对象，不存账号。首次时间和状态更新的区别以完整 DDL 为准；本地不再保留永久事件身份账本。

## 5. 服务端事件时间过滤

服务端以 occurred_at 判断事件是否处于允许接收的时间范围，重放、上传、接收和本地 created_at 均不能替代事件发生时间。已有事件重试沿用原 occurred_at 与 event_id；接收范围内重复仍依赖服务端唯一键，时间过滤不代替幂等。

本次只固定时间依据，不另设未经确认的接收截止值；服务端时间范围需兼容已约定的离线重试。并发上传可能乱序，不以最大收到的事件时间直接推断之前已经全部接收。被时间范围过滤的记录返回明确结果，不伪装为新接收成功。
