# TokenDance 团队功能与 UI 交互设计 v1

日期：2026-09-06。状态：设计提案，待产品评审；原型使用演示数据，未接入业务接口。

技术落地见 [团队模块技术方案 v1](tokendance-teams-technical-design-v1.md)，包含单团队数据库约束、创建与加入事务、API、统计授权和实施验收。

## 1. 定位与首版决策

让一组使用 AI 编程工具的人，共享经本人授权的用量统计，了解团队投入、工具构成和活跃情况。

核心闭环：**创建团队 → 邀请同伴 → 成员确认共享范围 → Collector 自动同步 → 查看团队趋势和成员贡献**。

目标用户优先为小型研发团队、工作室和学习小组。Token 数量衡量使用量，不代表代码质量、生产效率或绩效；界面使用「用量 / 贡献」，不使用「效率冠军 / 员工评分」。

建议首版决策：

- **确定规则：每个账号同时最多属于一个团队，所有者、管理员、成员均适用；创建团队也占用这唯一的名额。** 不提供多团队或团队切换功能。
- 团队默认为私有，仅成员可访问；公开团队主页和跨团队排行放到下一期。
- 使用所有者、管理员、成员三级固定权限，不设计自定义角色。
- 共享授权与公开排行榜相互独立。加入团队不自动公开个人资料。
- 用户可以只加入、不共享；开启共享时只纳入授权生效后的事件，不回填此前个人历史。
- 月度预算、通知机器人、组织层级、企业 SSO 暂不进入首版导航。

## 2. 现状依据与实现缺口

- `web/src/pages/teams/TeamDashboardPage.tsx` 当前仅为不可用占位页。
- 现有全站导航为 TokenBoard / 社区 / 团队，右侧头像进入个人数据和设置；团队页面延续该结构。
- 已有个人指标、趋势、Agent 分布、状态组件与中英文词典可复用。主色为 `#b9f600`，页面背景 `#f5f7f4`，正文 `#111512`。
- `team` 已出现在可见性枚举和排行榜 scope 中，但尚不构成完整的团队成员关系与授权系统。现有聚合任务中的 team scope 分支不能直接视作团队隔离实现。
- 本文在原用户产品方案的 P2 团队方向上单独定义 MVP。以下 P0 / P1 指团队模块内部优先级。

## 4. 信息架构

```text
全站导航：TokenBoard / 社区 / 团队                 个人头像菜单
                              │
                         /teams 入口
                ┌─────────────┴─────────────┐
             尚未加入                    已有团队
        创建团队 / 待处理邀请          /teams/:teamId
                                            │
                      总览 / 成员 / 用量分析 / 设置

邀请落地页：/teams/invitations/:invitationId
```

- `/teams`：未登录时展示简洁介绍与登录入口，保留 `return_to`；已登录无团队时展示创建入口和待处理邀请；已有团队时进入总览。
- `/teams/new`：独立创建团队页；进入和提交时都检查当前成员关系。已有团队时显示拦截页与「查看我的团队」，不展示可提交的创建表单。
- 总览默认近 7 日；提供近 30 日和自定义日期，右侧明确显示团队时区。自定义范围首版最多 90 天。
- 四个二级页签使用真实路由：`/teams/:id`、`/members`、`/usage`、`/settings`。
- 日期范围在总览、用量分析和成员统计之间保留，写入 URL；成员页「共享 / 同步状态」为当前状态，不能混作所选历史周期状态。
- 只有一个团队时显示静态团队身份，不增加没有用途的切换器。

## 5. 页面设计

### 5.0 无团队入口与创建团队页（本次补充）

创建团队采用独立页面。一级导航仍为 TokenBoard / 社区 / 团队；未创建前不展示总览 / 成员等团队内页签。

无团队入口 `/teams`：标题「和同伴一起记录 AI 用量」，主操作「创建团队」；已有待接受邀请时展示邀请列表。页面明确提示「每个账号只能创建或加入一个团队」，不添加通用邀请码框。

创建页 `/teams/new`：

- 页首「返回团队」、标题「创建你的团队」、说明「先给团队一个名字，成员可以稍后邀请」。
- 桌面左侧为单页表单，右侧为随输入更新的团队名片预览；手机表单在前，预览在后。
- 团队名称必填，2–40 个字符；简介选填，最多 120 个字符。名称去首尾空格后再校验，使用字素计数，避免中文 / Emoji 长度提示与提交不一致。
- 头像自动生成团队名首字，不要求上传；后续在团队设置中修改。
- 统计时区默认取账号时区，可在创建时选择；明确说明创建后固定、影响每日边界。
- 基础共享选填且默认关闭；仅在勾选后展示「成员贡献、Agent / 模型分类、费用」三个默认关闭的细项。没有共享授权也能正常创建。
- 表单末尾固定文字「每个账号只能创建或加入一个团队，创建后你将成为所有者」，不再要求一个没有独立意义的“同意限制”勾选框。
- 主按钮「创建团队」，次按钮「取消」。空名称 / 单字符 / 纯空格在字段下方解释并聚焦输入；输入保留，不只使用 toast。
- 提交时按钮变为「正在创建…」，冻结表单并防重复点击；失败恢复输入与操作。
- 创建成功进入团队首次使用页，展示团队名、所有者、1 位成员、共享状态，主操作「邀请成员」、次操作「进入团队」。邀请不属于创建的必填步骤。
- 首次总览显示「等待首次同步」或「尚未共享」，不填入其他团队的演示用量，也不将尚未收到数据展示成真实 0。

已有团队拦截：显示「你已经有一个团队」，展示当前团队和身份；主操作「查看我的团队」。普通成员 / 管理员需先退出当前团队；所有者需先转移所有权再退出，或解散团队。转移所有权本身不释放名额，不能自动帮用户离开当前团队。

### 5.1 总览

页头：团队头像、名称、简介、私有标记、当前角色；右侧一个主操作「邀请成员」，普通成员显示「我的共享」。

内容顺序：

1. 时间筛选、明确日期区间和「数据更新于…」。
2. 四项指标：团队 Token、活跃成员、当前共享成员、已记录费用。每项最多一行解释。
3. 左侧约 2/3 宽度为每日 Token 柱状趋势；右侧为 Agent 构成。手机上下堆叠。
4. 成员贡献列表，默认按本周期 Token 降序。点击姓名打开抽屉，仅显示其主动共享的团队指标。
5. 与当前数据相关的状态提示，例如「1 位成员尚未共享」「部分来源没有费用记录」，提供对应入口。

指标的显示规则：

- 「活跃成员」分子为周期内有有效共享 model_usage 事件的人数，分母为当前有效成员总数；说明分母时点。
- 「共享成员」表示当前已开启基础用量共享的人数；待接受邀请不计入成员数。
- 未共享成员列在成员页，贡献榜不对其显示零值、名次或推测数据。
- 费用以 `—` 表示不可用。来源有真实费用时显示「已记录费用」，只有估算时显示「估算费用」，两者不混加。不同币种分别显示。
- 费用旁显示覆盖率：可可靠关联该类费用的已授权有效 model_usage 事件数 / 本周期全部已授权有效 model_usage 事件数；未共享费用的用量仍计分母，独立费用事件不增加分母。悬浮可查看数量和定义。
- Token 总量与分布遵循已有标准化协议，禁止简单相加输入总量和已包含的缓存 Token。

### 5.2 成员

页内切换：「已加入 N」「待接受 N」。提供姓名 / Handle 搜索；邀请邮箱仅管理者在待接受列表中可见。

已加入表格：头像与昵称、角色、当前共享状态、团队同步状态、周期 Token、操作。

- 普通成员只看到已共享的汇总和已加入名单；看不到邀请邮箱及管理入口。
- 用户自行决定是否共享姓名关联的周期明细；未授权时展示「仅计入团队汇总」，不开放个人抽屉统计。
- 同步状态只反映已授权团队数据的新鲜度，不暴露个人设备列表、主机名、文件路径或账号凭据。
- 「尚未共享」与「尚无数据」「同步延迟」分别显示；不能把不愿共享解释为离线。
- 管理者从行内「管理」打开角色与移除操作；所有者行显示固定身份。
- 待接受邀请显示邮箱、拟加入角色、邀请时间、过期时间及撤销 / 重发；重发使旧邀请失效。

成员抽屉约 420 px：身份、加入时间、当前周期、授权范围、Token 与可用费用、Agent / 模型分布。未共享维度显示「成员未共享此项」；未采集显示「来源未提供」，两者区别对待。

### 5.3 用量分析

- 沿用全局日期范围，支持全部 Agent 或一个 Agent；模型选项依赖当前 Agent，切换不兼容 Agent 时清空模型筛选。
- 趋势、指标、分布及导出必须来自同一筛选条件与统计版本；不能只更新图表而保留旧数字。
- Agent / 模型维度未授权的贡献进入「未共享分类」合计桶，不展示来源身份，也不从总量中消失。
- 明细表字段：Agent / 模型、Token、占比、有效事件、费用类型与覆盖率；无支持的数据标记为缺失。
- 页面不展示会话正文、Prompt、回复、代码、仓库路径、密钥或机器信息。
- 管理者可导出 CSV，仅含当前可见的授权聚合数据、筛选范围、币种、数据截至时间及授权版本。普通成员仍从个人数据页导出自己的数据。

### 5.4 设置

设置页分三段，避免堆满通用设置：

1. 团队资料：名称、简介、头像、创建时确定的统计时区；所有者 / 管理员可编辑资料。首版时区创建后不可直接修改，避免历史口径漂移。
2. 我的共享：所有角色均可操作自己的授权；开关变更先暂存，点击「保存共享设置」生效。
3. 团队管理：仅展示当前角色允许的转移 / 退出 / 解散操作；最近操作记录只向管理者提供。

共享控件：

| 控件 | 初始值 | 含义 |
| --- | --- | --- |
| 将基础用量计入团队 | 关闭，加入时本人选择 | Token、有效事件、活跃天数等团队聚合 |
| 展示我的成员贡献 | 关闭 | 允许将昵称与周期 Token、活跃天数关联展示 |
| 共享 Agent / 模型分类 | 关闭 | 分类汇总；只有同时开启成员贡献才可关联个人展示 |
| 共享费用 | 关闭 | 现有已记录 / 估算费用分别汇总；受来源覆盖限制 |

基础共享关闭时，其他开关禁用且不产生实际授权；重新开启基础共享时不自动恢复其他开关。

开启新增维度仅对本次授权之后的数据生效，不追溯补共享。关闭某维度即时撤销该团队对相应历史维度的访问，再重建汇总；关闭成员贡献不影响仍然授权的团队汇总。

关闭基础共享时说明：「你的数据将从团队统计中移除，个人数据保留。重新开启后从新的授权时间开始统计。」用户确认后保存，不采用含糊的「暂停」文案。

## 6. 关键交互流程

### 创建团队

`创建团队 → 输入名称 / 简介 / 统计时区 → 选择自己的共享范围 → 确认创建 → 团队空总览 → 邀请成员`

- 名称 2–40 字符，简介 0–120 字符；身份使用稳定 team ID，团队名称不充当唯一标识。
- 时区默认取当前账户时区，并说明「影响全体成员的每日统计」。
- 不要求 Logo、不要求成员数量、不强制邀请；创建完可以稍后邀请。
- 提交期间按钮禁用；失败保留输入，错误紧贴字段或表单；重复提交由幂等键处理。
- 所有者同样需要本人授权共享，不能因创建团队自动读取个人历史。

### 邀请与接受

`邀请成员 → 邮箱 + 角色（默认成员） → 提交 → 待接受 → 收件人打开邀请 → 登录 / 注册 → 确认团队与共享范围 → 加入成功`

- 首版采用绑定邮箱、单次使用、7 天过期的邀请；一封邀请对应一个成员。
- 未登录先保留邀请，再登录；登录邮箱不匹配时提示切换账号。
- 接受页展示团队名、邀请人、拟授予角色、共享选项，允许「加入但暂不共享」。
- 已在其他团队：解释单团队规则并提供查看当前团队入口；不自动退出、不静默迁移。即使邀请早于当前成员关系，接受时仍需重新校验。
- 已加入当前团队：显示「你已是成员」并进入团队；重复打开不增加成员。
- 撤销、过期、团队解散和无效邀请分别有明确结果。过期页让收件人联系邀请人重发，不自动发送任何消息。
- 「邀请已创建」与「邮件已发送 / 发送失败」分开显示，失败可以重试；所有者降级邀请者权限后，未接受的管理员邀请需要重新校验。

### 改角色 / 移除 / 转移

- 管理员只能邀请和移除普通成员，不能提升管理员、管理所有者或其他管理员。
- 所有者可提升 / 降级管理员；转移所有权需选择一个有效成员，再输入团队名确认。成功后原所有者成为管理员。
- 转移过程必须保证任意时刻恰好一个所有者；移除、退出与转移并发时校验当前成员状态。
- 移除普通成员二次确认，展示昵称和「团队内数据将移除，个人数据保留」。
- 成员退出后立即失去团队访问权；所有者需先转移，若不转移则只能解散团队。
- 解散需输入团队名并再次确认；撤销所有邀请、团队授权及团队访问，不删除成员个人账户与原始个人数据。

## 7. 权限矩阵

| 操作 | 成员 | 管理员 | 所有者 |
| --- | --- | --- | --- |
| 看团队汇总和已加入名单 | 是 | 是 | 是 |
| 看成员主动授权的指标 | 是 | 是 | 是 |
| 修改自己的共享 | 是 | 是 | 是 |
| 修改他人的共享 | 否 | 否 | 否 |
| 邀请 / 撤销普通成员邀请 | 否 | 是 | 是 |
| 邀请管理员 / 修改角色 | 否 | 否 | 是 |
| 修改团队资料 | 否 | 是 | 是 |
| 移除普通成员 | 否 | 是 | 是 |
| 移除管理员 | 否 | 否 | 是 |
| 导出团队聚合 / 查看操作记录 | 否 | 是 | 是 |
| 主动退出 | 是 | 是 | 先转移 |
| 转移所有权 / 解散 | 否 | 否 | 是 |

权限以服务端判定为准，前端隐藏按钮只用于减少误操作。管理员身份不扩大成员数据授权。

## 8. 数据边界与异常状态

- 纳入团队的数据必须同时满足：有效成员关系、有效授权时间窗口、事件时间落在窗口内、对应维度仍获授权。
- 延迟上传按事件发生时间判定，而非上传时间；不接收离开团队后的新贡献。重新加入创建新关系 / 授权周期，旧历史不自动复活。
- 退出、移除、撤回共享或账号注销：立即阻断对应数据访问，增加授权版本；汇总、榜单、缓存、下载地址和正在生成的导出一并失效并重建。
- 重建完成前展示「共享范围已更新，正在重新汇总」，不得继续显示被撤销的旧汇总。已下载到用户本地的文件无法追回，导出前说明这一点。
- 已清理某用户历史后，历史曲线可能变化；明确标示「按当前授权范围统计」，不是不可变的财务账本。
- **单团队约束由服务端和数据库共同保证**：创建与接受邀请走同一原子名额占用流程。建议独立当前关系表以 `user_id` 为唯一键，历史成员关系另存；不能对历史表的全部 `user_id` 做唯一约束而阻止退出后再加入。
- 创建时，将团队、所有者关系和名额占用放在同一事务中；两个页面同时创建、创建与接受邀请并发、同时接受不同团队邀请，仅一个成功，失败事务不得留下无所有者团队。冲突返回 `409 TEAM_MEMBERSHIP_EXISTS` 与有权查看的当前团队入口。
- 待接受邀请不占名额，可以同时收到多封；接受其一后，其余邀请仍需遵守单团队限制。正常退出 / 被移除 / 解散生效后才能重新创建或加入；历史数据不自动迁移。重试同一成功请求应返回原结果，不创建第二个团队。
- 比较上周期使用同样授权和口径。若成员变化、授权窗口不足或上期无可比值，显示「暂无可比数据」，不伪造 +100%。
- 排名相同 Token 使用相同名次；其次按稳定 ID 排序以避免抖动。无授权者不参与排名。

| --- | --- | --- |

## 9. 视觉与交互规范

- 延续现有浅灰绿背景、白色面板、黑色文字、荧光绿主操作，不额外引入一套侧栏导航。
- 画布最大宽度沿用现有 1360 px；页内间距 24 px，模块 16–24 px；卡片圆角 14 px，输入与按钮 6–10 px。
- 标题 28–32 px、正文 14 px、说明 12–13 px；数值使用等宽数字。大数字控制在四项，避免复制个人页全部十项指标。
- 成员详细信息使用右侧抽屉；创建使用独立页面，邀请使用居中对话框；销毁操作单独确认。
- 对话框管理焦点、Esc 关闭、返回触发控件；表单错误保留输入；成功后更新数据并显示简短反馈。
- 360 px：指标两列、趋势和分布纵向、成员行转为紧凑卡片，详情变全宽；所有核心操作触控目标至少 44 px。
- 错误 / 未共享 / 离线不只靠颜色区分；图表数值可用键盘或触摸查看；支持减少动画偏好。
- 中英文使用现有 locale 机制，角色、状态、动态复数与日期统一翻译；不在中文界面混用英文操作词。

## 10. 开发拆分与验收

建议依次交付：

1. 团队 / 成员 / 邀请 / 授权的模型、服务端权限、创建和加入流程。
2. 成员关系与授权版本驱动的汇总、缓存失效、退出撤回、导出保护。
3. 总览、用量分析、成员抽屉、共享设置、中英文与响应式适配。

核心模型：`teams`、`team_memberships`、`user_current_teams`、`team_invitations`、`team_sharing_grants`、`team_audit_events`；快照、任务与删除屏障等完整结构见技术方案。沿用现有用户身份和采集事件，不复制个人账号。以下为已与技术方案对齐的计划接口，当前尚未实现：

- `GET /api/v1/me/team`，`POST /api/v1/teams`
- `GET/PATCH /api/v1/teams/:id`，`GET /api/v1/teams/:id/members`
- `POST /api/v1/teams/:id/invitations`，`POST /api/v1/team-invitations/:invitationId/accept`；邀请详情与接受均校验登录用户的验证邮箱。
- `GET /api/v1/teams/:id/analysis`，统一返回同一快照的指标、趋势与构成；成员周期详情与导出引用同一 snapshotId。
- `PATCH /api/v1/teams/:id/my-sharing`，`POST /api/v1/teams/:id/exports`
- 独立的 revoke invitation、role change、remove、leave、transfer、dissolve 操作接口；统一幂等和并发版本校验。

上线前必须验证：

- 未登录跳转后能回到原邀请；邮箱不匹配、过期、撤销和重复接受均正确。
- 普通成员无法直接调用管理 API；管理员无法升级自己或管理所有者。
- 不同 team ID 的查询、导出、缓存与榜单无越权；不能直接复用旧 team 枚举分支完成隔离。
- 私密个人资料可独立共享给团队，公开资料也不会自动共享给团队。
- 创建 / 加入默认无共享；所有新增维度从本人授权时刻起生效。
- 非成员、未授权维度、撤回历史及后台导出都遵守同一授权版本。
- 日期、Agent、模型变更后图表、列表、总量与导出一致；缺失费用不按 0 计。
- 退出、移除、解散、注销及所有权转移并发保持权限和唯一所有者正确。
- 任何角色都不能同时属于两个团队；创建 / 接受邀请的并发竞争、旧页面提交、幂等重试均不可绕过约束。所有权转移后，原所有者仍占用当前团队名额，须退出后才能加入另一个团队。
- 创建页空值 / 纯空格 / 字符长度校验、取消后返回入口、失败输入保留、共享默认关闭、创建成功仅一个成员、已有团队拦截均正确。
- 360 / 736 / 1024 px、键盘对话框、中文 / 英文状态文案通过验收。

## 11. 本轮交互预览覆盖

可体验总览 / 成员 / 用量分析 / 设置切换、7 / 30 日范围、成员搜索与详情、邀请创建 / 撤销、共享开关与撤回确认，以及角色和空团队状态的设计对比。

原型中的身份、数值、邀请和状态均为本地演示；不发送邮件、不修改真实团队。创建流程已补充独立交互预览；邀请接受、转移所有权、导出文件及后台重建以本文流程为准，属于后续业务实现。

本轮原型验证：已检查 360 / 736 / 1024 px 的浅色与深色布局，邀请创建与撤销、成员搜索、详情抽屉、日期切换、Agent 筛选、共享撤回确认均可操作。撤回演示用户的 8.4 M 贡献后，团队总量从 28.4 M 更新为 20.0 M，已记录费用从 $345.70 更新为 $233.30；此验证仅覆盖原型状态联动，不代表服务端授权或数据清理已经实现。
